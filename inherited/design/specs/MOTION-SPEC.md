# MOTION-SPEC: how every surface of the site moves (for builders)

*Written by W8, 2026-11-02, for W9 and every builder after it. **v1 adopted by the orchestrator, 2026-11-02 12:03 UTC**; W8 is its one writer, and every later change has a dated line under Changes. The evidence and the alternatives rejected are in `2026-11-02-W8-motion.md` beside this file (section numbers below point there). *

## 1. The rule this specification applies

Each surface moves only if its motion serves what that surface is for, and then in the way that serves it. A motion that suggests an event runs only on that real event: a new count, a call, a withdrawal, a viewer's own press. Nothing moves on a timer, while waiting, or for decoration. *Reason:* the maker's ruling of 2026-11-02 11:36 UTC ("Motion should satisfy its surface's purpose, not be there just because"); law 5 (a motion that signals an event is information only when the event is real).

The surfaces fall into six kinds of purpose, and the kinds want different things, not one curve at different lengths:

| Kind | What the motion is for | What that asks of the motion | Why (evidence, s. = section of the research file) |
|---|---|---|---|
| **Navigation** (the viewer goes somewhere) | keep the viewer's place; show where they went | starts on the same frame as the press, moves the whole view as one, settles slowly, never overshoots; going back is faster than going forward; can be interrupted | details.so's menus (the maker's loved case, W5 s.4.1); Apple's fluid interfaces (100% damping for a tap, symmetric paths, interruption); Material's shared axis for spatial relations (s.2) |
| **Feedback** (hover, press, focus) | confirm the input was taken | no travel and no duration: an instant change of state | frequency (Apple HIG, Atlassian, Kowalski, Rauno: motion on what happens dozens of times is removed); 0.1 s feels immediate (NN/g, RAIL) (s.2) |
| **Frequent data** (a new batch of votes) | show the current true figure | in a list of races: no motion. In the one race in focus: a short, small slide of the changed number, in the direction of the change | measured: per-number motion in a list is a flicker field that drops frames (s.3.1); results desks keep counts still (NPR's code, s.2); motion's signal value depends on its rarity (s.2) |
| **Decisive events** (a call, a withdrawal, a majority) | make sure the room sees that something was decided, and where | the one place the page draws the eye: a deliberate movement of the thing decided (a rule, a bar), simultaneous on every surface showing it, never overshooting, never repeating | Carbon's "expressive" motion "for occasional, important moments"; the delight curve (rarer, richer) (s.2); W5's prototypes (s.3.5) |
| **Status** (stale, error, loading, polls closing) | honesty about the state of the figures | words and tone, changed at once; never motion | a pulsing dot for nothing live is a named fault (`RULINGS.md`); motion implies an event, and a state is not one |
| **Catch-up** (a reload, a return to a hidden tab, a surface off screen) | show the present at once | everything applied without motion | none of it happened in front of the viewer; animating it would show events as arriving now when they did not (law 5) |

## 2. The tokens

A small set. Each has one purpose; a builder uses a token only for the surfaces named for it in section 3. Write them once, in one stylesheet, as custom properties; do not apply any of them globally. *Reason:* the maker's ruling that one motion everywhere will not work; a token used outside its purpose is the fault the ruling names.

```css
:root {
  /* the critically damped spring (no overshoot); its shape is the same at every length, W5 s.11.1, W8 s.3.5 */
  --spring: linear(0, 0.005 1.3%, 0.019 2.5%, 0.08 5.5%, 0.163 8.5%, 0.457 18.3%, 0.549 21.8%, 0.63 25.3%, 0.694 28.5%, 0.753 32%, 0.805 35.8%, 0.846 39.5%, 0.886 44%, 0.919 49%, 0.944 54.5%, 0.964 60.8%, 0.988 75.5%, 1);
  --ease-out-strong: cubic-bezier(.17, .84, .44, 1);   /* details.so's closing curve, W5 s.4.1 */
  --ease-sheet: cubic-bezier(.32, .72, 0, 1);         /* Vaul's iOS-matched drawer curve, s.2 */

  --m-nav-in-dur: 680ms;      /* omega 12.5 rad/s, details.so's own; 50% at 134 ms, within 1% at 531 ms */
  --m-nav-back-dur: 450ms;    /* with --ease-out-strong */
  --m-count-dur: 240ms;       /* with --ease-out-strong; legible again by about 100 ms */
  --m-call-dur: 680ms;        /* with --spring */
  --m-call-color-dur: 300ms;  /* with --spring; Material's slow effects spring settles in 235 ms */
  --m-uncall-dur: 450ms;      /* with --ease-out-strong */
  --m-insert-dur: 510ms;      /* with --spring; within 1% at 400 ms */
  --m-reorder-dur: 410ms;     /* with --spring; within 1% at 320 ms */
  --m-segment-dur: 300ms;     /* with --spring; a segmented switch's indicator (surface 37) */
  --m-reveal-dur: 160ms;      /* with ease-out, opacity only */
  --m-sheet-dur: 500ms;       /* with --ease-sheet */
  --m-card-open-dur: 500ms;   /* phone card rising, with --ease-sheet */
  --m-card-close-dur: 350ms;  /* phone card closing, with --ease-sheet */
  --m-drawer-open-dur: 400ms; /* side menu opening, with --ease-sheet (about half a card's travel, so shorter: Material, duration with distance) */
  --m-drawer-close-dur: 300ms;/* side menu closing */
  --m-fade-out-dur: 100ms;    /* page change, old view out, ease-in */
  --m-fade-in-dur: 200ms;     /* page change, new view in once painted, ease-out */
  --m-axis-out-dur: 120ms;    /* deeper from a list (desktop): old view 24 px toward the start, fading out, ease-in */
  --m-axis-in-dur: 240ms;     /* new view from 24 px toward the end, fading in, --ease-out-strong */
  /* the fading band on arriving counts (surfaces 11, 15): not an animation; its opacity is set at each poll from the figure's age */
  --band: #faf2d8;            /* dark scheme: #2c2716. every text colour on it keeps 4.5:1 or more; in light its relative luminance stays above 0.80 and in dark it differs from the page by under 0.10, so it can never count as a flash (WCAG 2.3.1) */
  --band-hold: 7s;            /* full strength through one poll interval */
  --band-fade: 120s;          /* then an even fade to nothing; 120 s is civicAPI's slowest sweep (state legislatures), so no band means the figure has not changed through a full sweep */
}
```

Browsers without `linear()` (before Chrome 113, Safari 17.2, Firefox 112) get `cubic-bezier(.17,.84,.44,1)` in its place: put the fallback first and the `linear()` declaration after it, or in script test `CSS.supports('transition-timing-function', 'linear(0, 1)')`.

**The time at which `--spring` reaches a fraction** (for surface 3's majority mark). The stops are the `linear()` string's own:

```js
const SPRING_STOPS = [[0,0],[.005,.013],[.019,.025],[.08,.055],[.163,.085],[.457,.183],[.549,.218],[.63,.253],[.694,.285],[.753,.32],[.805,.358],[.846,.395],[.886,.44],[.919,.49],[.944,.545],[.964,.608],[.988,.755],[1,1]]; // [value, time fraction]
export function springTimeAt(f, duration) { // f: 0..1 of the movement; returns ms
  for (let i = 1; i < SPRING_STOPS.length; i++) { const [v1, t1] = SPRING_STOPS[i], [v0, t0] = SPRING_STOPS[i - 1];
    if (f <= v1) return duration * (t0 + (t1 - t0) * (f - v0) / (v1 - v0)); }
  return duration;
}
// a segment growing from scale s0 to 1 crosses the mark when its scale is sm: springTimeAt((sm - s0) / (1 - s0), 680)
```

## 4. How to build it (rules that apply to every token)

1. **Only `transform` and `opacity` move**; colour fills may change by `fill` or `background-color` (they do not cause layout). Never animate `width`, `height`, `top`, `left`, `flex-basis`, `max-height`. *Reason:* layout-bound animation drops frames on phones (web.dev, Vercel, Atlassian, s.2); measured the cost here (s.3.1, 3.4).
2. **Few animations at once.** One transform on the map group, one opacity on the "rest" group: not one per shape. *Reason:* measured, 0 against 6 to 9 dropped frames per zoom (s.3.4).
3. **Never `transition: all`**, never a global transition or a shared helper applied to every component. Each component attaches its own token to its own property. *Reason:* the ruling; W9's brief.
4. **Interruptible.** Use the Web Animations API (`element.animate`) or CSS transitions, not CSS keyframe animations, for anything a press can interrupt; on a new press, read the current computed transform, `cancel()` the running animation and start from there. *Reason:* s.2 (Apple 803; Kowalski: transitions retarget, keyframes do not).
5. **Data that lands during a navigation motion** is written to the page at once and does not animate (the view is moving anyway; its own motion would compete). A call that lands mid-zoom on the state being zoomed to is shown in its final state when the zoom settles.
6. **No stagger anywhere.** Simultaneous events move simultaneously. *Reason:* staggering delays information (law 2) and does not help tracking (Chevalier, Dragicevic & Franconeri 2014: "negligible, or even negative", s.2); a stagger of a batch of calls measured as streaming text (s.3.2).
7. **One event, every surface, the same moment.** A call moves its card's rule, its seat bar, its map fill and its calls entry together, each with its own token. *Reason:* each surface must be true at once (law 2); delaying one to stage a sequence would show a false state on it.
8. **Text never travels or fades across text.** A whole view may move or fade as one in navigation (10, 13, 35), never overlapping another view's text; inside a view, labels and panel contents are swapped at once; the only text that moves is the changed number in the race in focus (`count`) and new calls entering (`insert`). *Reason:* crossfaded text overprints (W5 s.11.2, 14.3; s.3.3).
9. **Tabular figures everywhere figures change** (`font-variant-numeric: tabular-nums`). *Reason:* a number that changes width shifts its neighbours, which is motion on every update (GOV.UK's own reason, s.2).
10. **Accessibility in markup, not motion.** One empty `role="status"` region (polite) in the initial page announces calls, batching all calls seen in one poll into one sentence; counts and the calls list are not live regions; navigation moves focus to the new view's heading (`tabindex="-1"`) and sets `document.title`; back returns focus to what opened it; focus moves at the start of a motion, never after it. *Reason:* WAI-ARIA 1.2, APG, WCAG 4.1.3, Gatsby/Fable testing (s.2); Atlassian: focus and announcements "at the start of the animation".
11. **Check before merging** (and for rule 12, a check on the phone profile, 390x844 at 3x with CPU slowed fourfold: from the tap to the first presented frame that shows the mover away from its start under 150 ms (100 on the desktop), and no gap over 50 ms between the compositor's frames from that frame to the settle, read from `Page.startScreencast` frame timestamps; v1.8.7, research s.20.11: a frame after `animate()` that does not yet show the motion is not its first frame): a Playwright test that loads the country view, applies a poll changing at least seven list races, and asserts that `document.getAnimations().length` is 0 afterwards (surface 11 has no motion); one that applies a call and asserts each animation's `effect.getTiming().duration` matches its token; one with `reducedMotion: 'reduce'` (Playwright's `emulateMedia`) asserting no animation of `transform` runs on navigation. *Reason:* "for agents": a rule a test enforces is not lost when the next builder arrives. **Heights (added 12:57 UTC after the maker's 12:50, research s.53):** the phone's checks also run at 390×664 and 360×640 with ten pins on the fixtures night, and any surface that can hold more than a screen (the menu, a card, a sheet) is checked there for what falls below the screen and for its own scroll under a finger (`drawerscroll.mjs`).
12. **The press moves first; nothing heavy runs during a motion.** A navigation's motion starts within 100 ms of the press, from what is already drawn, and the incoming view's first screen is rendered and painted before its motion starts. Fetch the next view's data on the intent to press (a pointer resting on a state, `pointerdown` or `touchstart` on a tile), not on the click; render what lies below the first screen after the motion's `finished`, in chunks that each take under 50 ms (the chunk is the build's own work: its script and what it asks the browser to lay out and paint in one frame, so a section is drawn a few rows a frame; measured on the phone profile, a frame that paints a section of rows costs 50 to 100 ms of the browser's own render on this container, which no file boundary moves, research s.20.10). **A motion's clock starts on the frame in which its first frame is presented, never before** (v1.8.7): if the compositor cannot present the motion's first frame within the start's budget, the motion waits for that frame and then runs whole; it does not run its first frames unseen. *Reason:* measured on W9's zoom into a race (research s.20.11): the animation's clock ran from 7 ms after the press while no frame was presented for 100 ms, so the first frame the viewer saw was the copy 100 ms into its spring, and the start was lost, not late. If the first screen cannot be ready in 100 ms, show the press at once (surface 9) and start the motion when it is ready, never with an unpainted view. The check runs locally and on the deployed preview, because the network's part of a press (the fetch on the intent to press) shows only there (research s.15, s.20.6, s.20.8). **A drawer or card is the same** (surfaces 6, 10 P, 13 P, 34, and the night card of 32 P): its contents are mounted once its code has loaded and kept out of view (not unmounted and not `hidden`, so they are already laid out), so the press only starts the motion; the page-wide work of a modal (the scroll lock, marking the rest of the page hidden from assistive technology) is applied when the opening's `finished` resolves, while focus moves into the drawer at once and its focus trap holds from the press. **Under reduced motion there is no `finished`:** the placed view is shown first, a frame is painted with it, and only then do the rest of the view and the modal's page-wide work run (v1.8.5). *Reason (reduced, v1.8.5):* measured on W9's cards (research file s.20.3 and s.20.4): with no animation the rest of the card and the page lock ran before the card was shown, and then in the same frame as its showing, in tasks of 60 to 100 ms back to back, so the viewer who asked for no motion saw nothing for 450 to 600 ms after the press where section 5 says the change at once. *Reason (drawers, v1.8.2):* measured on W9's side menu (research file s.14): on the phone profile the menu's 160 nodes were mounted on the press (an 87 ms task) and the motion began 155 to 188 ms after it; then the scroll lock and the hiding of the page's header and main ran inside the motion (a 114 ms task), and the compositor's frames stopped for up to 137 ms; on the desktop the start was 24 to 30 ms but the same work left 64 to 74 ms gaps. *Reason:* measured on W9's page (research file s.8, with its correction): on the phone stand-in the push began about 100 ms after the press but the compositor's frames stopped for 111 to 168 ms inside it, and the incoming page slid in before its body was painted, so the country showed through under its heading (text over text, rule 8); the back began 178 to 218 ms after the press; the desktop zoom began 112 to 138 ms after the press at full speed. Response within 100 ms (RAIL, NN/g, s.2) is the purpose of the motion: it says the press was taken.

## 5. Reduced motion

Write the still version first; add motion only inside `@media (prefers-reduced-motion: no-preference)`, and in script read `matchMedia('(prefers-reduced-motion: reduce)')` and listen for its `change` (the setting can change while the page is open). Under `reduce`: every `transform` motion (zoom, push, slide, sheet, bar growth, tint sweep, row reorder, number slide, smooth scroll) is replaced by the change at once; colour changes (`call-color`) and the 160 ms `reveal` stay, because colour and opacity that do not change size, shape or position are not motion animation (WCAG 2.3.3's definition) and keep the event visible. Each navigation moves focus to the new heading so the change is still announced. *Reason:* WCAG 2.3.3 and its sufficient technique C39; Media Queries 5's definition; WebKit's trigger list (scaling and zooming, large-area and peripheral motion) and its "Don't Reduce Too Much"; Apple's "replace transitions in x, y and z with fades"; Comeau against a global `0.01ms` kill switch (s.2).

## 6. Never

1. Nothing moves without a real event: no idle motion, no loop, no pulse, no "live" dot, no shimmer, no spinner, no jitter. (The NYT needle's jitter of 2016 was read as data and called "an artificially added dramatic element"; the Times dropped it by 2018, s.2.)
2. No overshoot, bounce or elastic curve on anything that shows a count, a seat or a threshold.
3. No per-digit rolling and no counting through intermediate values.
4. No per-number motion in lists of races. No highlight that appears without a new count, fades in, repeats, pulses, glows or advances its fade between polls.
5. No stagger; no batch streaming more than one row past the eye.
6. No crossfade of text over text.
7. No hover effects on touch screens; no hover glow, shadow, lift or moving arrow anywhere (`RULINGS.md`).
8. No text that scrolls across the screen, including a long smooth scroll.
9. No `transition: all`; no animation of layout properties (two dated exceptions, 40 and 34, each measured and each on an element whose size change reflows nothing else or only what the viewer pressed); no global motion helper; no global reduced-motion kill switch (`* { animation: none !important; transition: none !important }`): it also removes the colour and opacity changes section 5 keeps, and does not touch script animation anyway.
10. No motion for events that happened while the viewer was away (hidden tab, off screen, reload).
11. No animation on a back gesture the browser has already animated.
12. No transition of colours page-wide on a change of scheme (surface 36): a 200 ms transition on every element froze the phone at 4x for 700 ms and ran four long tasks on the desktop (research s.22.1).
